### Bug fix

**You own this task. Plan, review, verify.** Delegate investigation and the fix to subagents, stay in the lead.

Be scientific. Every shipped line traces to runtime evidence. Belt-and-suspenders that "might help" is a hypothesis, not a fix. It does not ship. When evidence refutes a hypothesis, revert what it motivated. The smallest change the evidence justifies ships, nothing more.

1. Reproduce it yourself on the real surface, even when a debug or instrumentation protocol says to ask the user to reproduce. If the repo has a `verify-*` skill for that surface, drive through it. Otherwise drive the app, the CLI, or the test yourself. Ask the user only with a stated, specific reason that surface cannot be driven, and only after driving it as far as it goes. If it won't reproduce directly, synthesize the trigger, tighten conditions, or instrument until it fires. Build the repro as a feedback loop with a pass and fail signal, per `../references/feedback-loops.md`, and capture the symptom verbatim.
2. Binary-search the cause. Write 3 to 5 ranked hypotheses before testing any. Each is falsifiable and names its prediction, such as "if X is the cause, changing Y makes the bug disappear". Keep them in a table of rank, hypothesis, prediction, and status (open, confirmed, rejected), and update it as evidence comes in. Rule them out until one survives. Seed them with `how` over the affected subsystem and the **why** skill for regression history. Each pass, take the split that cuts the most remaining problem space, get runtime evidence, eliminate. When program state is unclear, add instrumentation or logging and read it as the code runs. Don't guess. Each probe tests one hypothesis's prediction and changes one variable. Prefer a debugger or REPL, then targeted logs at the hypothesis boundary. Never log everything. Tag every probe line `[DEBUG-<id>]` so step 4 can find it. Drive a long or stubborn hunt with Cursor's `/loop` command. Confirm the surviving *mechanism* with runtime evidence before the step-3 architect/challenge fan-out.
3. Plan the fix. Before you edit, grep every caller of the function you touch and fix the shared code once, per the **fix-root-causes** principle skill. A fix in only the path the report names leaves the other callers broken. If it crosses a function boundary, `architect` first. Delegate implementation to a subagent with a specific scope. Read `spawn-subagent`. Role line `bug-fix`.
4. Verify on the same surface. The original repro now passes. "Inconclusive" or wrong-surface is not a pass. Flag it. Unit tests show branch behavior, not bug absence. Then clean up. `rg '\[DEBUG-'` over the tree returns nothing, and throwaway harnesses are deleted.
5. Stage the commits with the **git-commit** skill so the failing repro lands before the fix in git history. When the bug has a cheap local test path, land that failing repro first with the **tdd** skill. Skip it when the test would be expensive, integration-heavy, or unclear.
   This is the canonical **sequence-verifiable-units** principle skill, the failing test first and the fix on top.
6. Run **Opening a PR**.

**Reply:** what was broken, root cause, fix, how you verified. Paste failing-then-passing repro output verbatim. Name the rejected hypotheses and the evidence that ruled each out. Say what would have prevented the bug. When the answer is structural, such as a missing test seam or tangled callers, name it as follow-up work, not part of this fix.
