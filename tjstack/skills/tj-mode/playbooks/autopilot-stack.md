### Autopilot-stack

**You own the stack, never the landing. Build and verify the queue with full autonomy, then hand the operator one linear base-branch stack to review and land.** "MR" also means a GitHub pull request.

1. **Run one owner per MR.** Print the Destination tuple once per `playbooks/opening-a-pr.md`. Every owner reuses it. Spawn one `tj-agent` per MR per `spawn-subagent`. Within about 15 minutes, the owner starts a **track-your-work** trail, pushes its first snapshot, and opens its MR ready through **Opening a PR**. Then it proves the change on the real artifact, triages reviews skeptically, runs **noslop** and **clean-comments**, and babysits its own MR in `drive` per `playbooks/babysit.md`. It pushes after every verifiable unit. For each subagent it starts, it adds the ID, expected runtime (at least the longest past run of that kind), and state to `children.tsv`. The trail and `children.tsv` live uncommitted under `.audit/` in the owner's checkout. A local root reads them there. A cloud owner returns them with each report.
2. **Audit on a real loop.** On the operator's go, the root arms `/loop 1h` with a prompt that runs this tick. Each tick re-reads this playbook from its installed path beside the tj-mode `SKILL.md` loaded this session, audits the run against it, and fixes drift. Count only side effects as progress: pushes, MR and pipeline changes. For a local owner, `git -C <worktree> log` counts too. An owner or `children.tsv` entry that errors, or passes its expected runtime with no side effect, is stuck. Stop it and replace it with a fresh agent carrying the consolidated scope. The owner replaces its stuck children, and the root does when the owner cannot. After a Cursor restart, replace every local owner from its pushed branch.
3. **Hold the operator gates.** State the plan, then wait. A request to state the plan is not a go. On the operator's stop, every owner stops writing at once.
4. **Verify each round.** The owner reports its code-ready head SHA when the shipped code is final, and each later push that changes the patch. At that SHA, the root runs these lanes per the **swarm** skill, on a model family other than the owner's, from a `spawn-subagent` role line:
   - Re-run the gates.
   - Prove the load-bearing behavior live on the real surface, with `control-cli` or `control-ui` if installed. Without this lane, no verdict is clean.
   - Audit the diff in two or more lanes, each with one focus (consumer parity, races, data safety), distrusting the MR body.
   - Run the same scenario on current trunk as the regression lane.

   Send all proven findings to the owner in one fix round, each with a red test or repro receipt. The owner reports STACK-READY with the exact head SHA when its babysit is green.
5. **Append on a clean verdict, never land.** A clean verdict appends the MR to the stack, in verified order or the operator's. No owner or root merges, arms auto-merge, or closes an MR.
6. **The root alone writes topology.** Owners push only their own branches and report the tip, base, and intended parent. To append, the owner holds writes and the root rebases the child onto the exact parent tip. It reads the remote tip with `git ls-remote <remote> refs/heads/<branch>` and pushes with `git push --force-with-lease=<branch>:<sha> <remote> <branch>`, where `<sha>` is that tip. The owner then resets to the pushed tip. Print the Destination tuple before every create or retarget. Create with the stack child command in `playbooks/opening-a-pr.md`. Retarget with `glab mr update <n> -R https://<host>/<project-path> --target-branch <parent>` or `gh pr edit <n> --repo <owner>/<repo> --base <parent>`. Only the bottom MR targets trunk.
7. **Absorb drift at the root.** The root fetches trunk and rebases the chain bottom to top. A fresh owner resolves each conflicting link. Record each verdict's head SHA, base SHA, and `git diff <base>..<head> | git patch-id --stable`. A rebase keeps a verdict only when that patch-id is unchanged at the new SHAs, and mergeability and the pipeline still run again. A changed patch-id sends the link back to step 4. A genuinely new raise of a gate or budget value is an operator gate, named in the MR body.
8. **Deliver the chain.** The operator gets one linear chain of verified MRs, reviewable bottom-up. Each link carries its verdict and head SHA in the MR body or a comment. The operator reviews and lands it. After each operator merge, the root rebases the rest only when the operator asks.

**Routing.** One MR is Feature plus **Opening a PR**. Independent MRs with no order are separate Feature runs. A coupled or ordered queue belongs here.

**Reply:** links to the bottom and top MR, each link's verdict and head SHA, where the trails live, and anything parked with the reason.
